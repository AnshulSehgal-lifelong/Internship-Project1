Goal:
Create a global search bar where users/admins can search anything across the application from a single input field.

The search system should support:
- Full-text search
- Ranked results
- Fast querying
- Typo tolerance
- Partial matching
- Multi-entity search
- Scalable architecture

Architecture Overview:
The system should NOT directly search across all tables using JOIN-heavy queries.

Instead:
1. Create a centralized denormalized search table (summary/search_documents table)
2. Aggregate searchable data from all entities into this table
3. Use PostgreSQL full-text search with tsvector
4. Add GIN indexes for fast search performance
5. Add trigram search for typo tolerance and fuzzy matching
6. Build a FastAPI search API
7. Connect the API to a debounced Next.js search bar
8. use proper triggers to update the indexes and summary tables as new data is being inserted

Core Database Design:
Create a table similar to:

search_documents:
- id
- entity_type
- entity_id
- title
- content
- metadata/jsonb
- search_vector (tsvector)
- created_at
- updated_at

Requirements:
1. PostgreSQL Full Text Search
- Use to_tsvector()
- Use plainto_tsquery() or websearch_to_tsquery()
- Use ts_rank() for ranking

2. Weighted Search
Prioritize:
- titles
- usernames
- important fields
over descriptions/content

Use:
- setweight(..., 'A')
- setweight(..., 'B')

3. GIN Indexing
Create optimized GIN indexes on:
- search_vector
- trigram searchable fields

4. Trigram Search
Enable:
CREATE EXTENSION pg_trgm;

Use trigram indexes for:
- typo tolerance
- fuzzy matching
- autocomplete-like behavior

5. Search Syncing Strategy
Implement backend-managed indexing:
- Whenever an entity is created/updated/deleted
- FastAPI updates the search_documents table

Avoid complex DB triggers initially.

6. FastAPI Search API
Create:
GET /search?q=

The API should:
- sanitize input
- build tsquery
- rank results
- combine full-text + trigram search
- return grouped entity results

7. Ranking Logic
Results should rank based on:
- title match priority
- exact matches
- weighted fields
- fuzzy similarity
- recency (optional)

8. Frontend Search UX
In Next.js:
- use the searchbar in the header
- use debouncing (~300ms)
- async API requests
- dropdown suggestions
- grouped results by entity type
- keyboard navigation support

9. Performance Requirements
The system should:
- scale efficiently
- avoid full table scans
- avoid heavy runtime joins
- use indexed search queries only

10. Future Scalability
Design architecture so it can later support:
- Elasticsearch/OpenSearch
- semantic/vector search
- embeddings
- hybrid search pipelines

Deliverables:
- PostgreSQL schema
- SQLAlchemy models
- Alembic migrations
- Search indexing service
- FastAPI routes/services
- Search ranking logic
- Trigram + GIN setup
- Example queries
- API integration
- Folder structure
- Production-ready architecture explanation

Important:
Focus on PostgreSQL-native search first before introducing Elasticsearch.
The solution should be clean, scalable, and production-ready.
